# 状态更新（2026-11-16 04:40）：纯透传仍崩，责任不在 hook

## 本轮实验结果

| 配置 | 结果 |
|---|---|
| 自编译 so + `disable_dlopen_hook` + 禁全部 hook + 关 GUI | `Load ... ok` → `Game region: China` → `dlopen hook disabled by config` → `JNI_OnLoad` → **SIGBUS(status=7)** |
| 自编译 so + `passthrough_only`（连 hook::init 都不执行） | `Load ... ok` → `passthrough_only: skip hook::init` → **SIGSEGV(status=11)** |
| 同上，但改用动态 `libc++_shared` 重新链接 | 仍然 **SIGSEGV(status=11)** |

结论：**只要把 Hachimi 顶掉 `libmain.so` 这一个位置，Unity 初始化就会崩**，与是否 hook、用静态还是动态 libc++ 都无关。

## 说明什么

问题不在 Hachimi 的逻辑，而在「**替换 libmain.so 这个加载位置**」本身：

- `libmain.so`（我们的 Hachimi）被 classloader 加载 → `JNI_OnLoad` → `dlopen("libmain_orig.so")` → 调用原版入口
- 原版 Unity libmain 可能依赖「自己是 `libmain.so`」这个身份（`dladdr` 取自身路径、按 soname 找依赖）
- 一旦它从 `libmain_orig.so` 这个别名被加载，Unity 内部解析就会错位 → 初始化阶段崩

## 下一步更靠谱的方向：**不要在 libmain 位置动手，改成"晚加载"**

思路：让游戏正常加载原版 `libmain.so`（不做任何替换），等 `libil2cpp.so` / `libunity.so` 已经加载后，
再把 Hachimi 作为**普通附加库**塞进进程：

1. 容器里保留 `nativeLibraryDir` 重定向（已可用），但 `libmain.so` 用**原版软链**（不替换）
2. 新增一个 `libhachimi_entry.so`（就是 Hachimi 的 so，改名），在
   `System.loadLibrary("il2cpp")` 之后、或 Unity 第一帧之后由 Java 侧 `System.load()` 加载
3. Hachimi 的 `JNI_OnLoad` 会 `dlopen("libmain_orig.so")`；此时把 `libmain_orig.so` 软链到原版 `libmain.so` 即可满足它
4. 这样 Unity 的加载路径完全不变，Hachimi 只是"搭车"

需要改的只有容器里的加载时机（Java 侧），**不用再改 Hachimi 源码**。

## 备选：彻底不用 Hachimi 核心

按 `docs/CN-PLUGIN-ADAPTATION.md` 的路线，自己写一个最小 so：
- 只做 `il2cpp_*` 按名字解析 + 少量需要的 hook（帧率、剧情快进）
- 不碰 linker、不替换 libmain

成本高但可控，且天然规避上面所有问题。
